# SONARA ANDROID — PRE-IMPLEMENTATION AUDIT 01
## Android Project Folder & Package Structure Specification

---

## 1. Executive Summary & Objective

This document establishes the authoritative **Project Folder & Package Structure Specification** for Sonara Android prior to code implementation.

Sonara Android is an open-source, Android-first music streaming and catalog application built with Kotlin, Jetpack Compose, Material 3, and AndroidX Media3 (ExoPlayer + MediaSessionService). The architectural foundations established in **Phases 4A, 4B-1, 4B-2, 4B-3, 4C, and 4D** define rigorous boundaries across UI (UDF, state-driven, presentation error mapping), Playback (MediaSessionService, single-authority ExoPlayer, RefreshingDataSource, ContinuityEngine), Data (Single Source of Truth repositories, Room, Proto DataStore, multi-provider networking), and Networking Resilience (acyclic provider fallback, bounded stall recovery, direction-neutral transition versioning).

The primary question addressed by this audit is:
> **"Where should every architectural responsibility physically live in the codebase to maximize clarity, testability, and maintainability while strictly enforcing unidirectional dependencies without unnecessary boilerplate?"**

## 4. Step 3: Structural Strategy Evaluation

Three structural patterns were evaluated for Sonara Android:

```text
STRATEGY A: LAYER-FIRST              STRATEGY B: FEATURE-FIRST            STRATEGY C: HYBRID (RECOMMENDED)
├── data/                            ├── home/                            ├── core/ (cross-cutting)
│   ├── local/                       │   ├── ui/                          ├── domain/ (pure models/ports/algorithms)
│   ├── remote/                      │   ├── data/                        ├── data/ (repos/local/remote)
│   └── repository/                  │   └── domain/                      ├── playback/ (Media3 service subsystem)
├── domain/                          ├── player/                          └── feature/ (UI & ViewModels by screen)
│   ├── model/                       │   ├── service/                         ├── home/
│   └── repository/                  │   └── ui/                              ├── search/
└── ui/                              └── search/                              ├── player/
    ├── home/                            ├── data/                            └── library/
    ├── player/                          └── ui/
    └── search/
```

### 4.1 Strategy Analysis

| Criteria | Strategy A: Layer-First | Strategy B: Pure Feature-First | Strategy C: Hybrid Layer-Feature (RECOMMENDED) |
| :--- | :--- | :--- | :--- |
| **Description** | Top-level packages are purely architectural layers (`ui`, `domain`, `data`). | Every top-level package is a standalone feature containing its own UI, Data, and Domain. | Shared infrastructure (`core`, `domain`, `data`, `playback`) lives at root; UI and ViewModels are grouped by feature. |
| **Advantages** | Strict layer boundaries; easy to verify dependency rules at package level. | High cohesion per feature; easy to delete or isolate a feature. | **Matches Sonara's architecture perfectly**: Data and Playback are shared subsystems (a `Track` belongs to Home, Search, Library, and Player alike). UI remains modular. |
| **Disadvantages** | UI packages become deep; feature screens are separated from their specific ViewModels. | Severe fragmentation of shared music entities (`Track`, `Album`), database tables, and playback services across unrelated feature folders. | Requires discipline to prevent feature-to-feature cross coupling. |
| **Media3 / Playback Fit** | Weak: Playback service is awkward to place inside generic UI or Data. | Very Poor: Playback is a central singleton system service, not a UI feature. | **Excellent**: `playback` is elevated to a first-class subsystem package alongside `data` and `feature`. |
| **Domain Sharing** | High | Low (massive duplication or awkward cross-feature imports) | High (centralized pure domain models, algorithms, and ports). |

### 4.2 Recommendation
**Strategy C (Hybrid Layer-Feature Architecture)** is officially selected.
In a music player application, data models (`Track`, `Album`, `Artist`, `Queue`) and the playback engine (`SonaraPlaybackService`, `ExoPlayer`, `StreamResolverPort`) are inherently shared across all screens (Home, Search, Library, Player, Queue). Isolating data or playback inside individual UI feature folders creates severe circular dependencies. Strategy C gives `domain`, `data`, and `playback` their dedicated architectural homes while organizing the UI layer cleanly by user-facing feature.

## 7. Step 6: Architectural Decision Rules (Explicit Boundaries)

### 7.1 The Explicit UseCase Decision Rule
To avoid the boilerplate trap of generating redundant 1-line pass-through UseCases that simply mirror repository methods (violating clean code and YAGNI principles):

1. **Default Pattern (Direct Repository Access)**:
   - ViewModels MUST directly inject and observe `domain.repository` interfaces for simple 1:1 data queries and operations (e.g., `catalogRepository.getTrack(id)`, `libraryRepository.observeLikedSongs()`, `searchRepository.search(query)`).
2. **Mandatory UseCase Rule**:
   - A dedicated UseCase class in `domain.usecase.<subsystem>` is STRICTLY MANDATORY if and only if:
     - **Multi-Repository Coordination**: The operation coordinates mutations across 2 or more distinct repositories (e.g., adding a track to a playlist while simultaneously writing an entry to history and updating playback stats).
     - **Complex Domain Business Rules**: Non-trivial domain validation, deduplication algorithms, or policy transformations must execute before data reaches persistence or presentation.
     - **Shared Multi-ViewModel Logic**: The exact same multi-step business workflow is executed by multiple different ViewModels or background workers.

### 7.2 The Strict `core.ui` Containment Rule
To prevent `core.ui` from degenerating into a generic, disorganized component dumping ground:

1. **ALLOWED in `core.ui`**:
   - **Design System Tokens**: Colors (`Theme.kt`, `Color.kt`), Typography (`Type.kt`), Shapes, Elevation, Alpha tokens.
   - **Generic Presentation Primitives**: `UiText` (sealed class wrapping string resources vs raw strings), `Modifier` utility extensions.
   - **Universal Atomic Components**: Base design-system primitives that contain zero business logic and are used universally across the app (e.g., `SonaraButton`, `SonaraSurface`, `SonaraLoadingSpinner`, `SonaraErrorBanner`).
2. **STRICTLY FORBIDDEN in `core.ui`**:
   - **Feature-Specific Composables**: Components like `MiniPlayer`, `Scrubber`, `QueueListItem`, `LyricsLineItem`, `SearchResultHeader`, `AlbumHeader` MUST live in their respective `feature/<name>/components/` packages.
   - **Composables with ViewModel / Navigation Dependencies**: No component in `core.ui` may accept a ViewModel, Navigation Controller, or domain repository as a parameter.

### 7.3 ContinuityEngine Dependency Boundary
`ContinuityEngineImpl` (in `playback.continuity`) has a strictly defined architectural boundary:
- **Implements**: `domain.ports.ContinuityEnginePort`.
- **Inputs**: Receives seed track metadata and playback context (`lastTrackId`, `playedTrackIds`).
- **Dependencies**: Injects `domain.repository.CatalogRepository` to fetch recommendation batches.
- **Forbidden**: It MUST NOT hold a direct reference to `ExoPlayer`, `SonaraPlaybackService`, or the active playback queue state. It returns recommended domain `Track` items back to `QueueManager` / `PlaybackController` for queue insertion.

## 8. Step 7: Playback Subsystem Audit

Playback is the most sensitive area in Sonara. In accordance with Phase 4B-1 and Phase 4D, its components are allocated to distinct subpackages within `playback`:

```text
playback/
├── service/
│   └── SonaraPlaybackService.kt       # Hosts MediaSession, runs in foreground, survives UI death
├── player/
│   ├── ExoPlayerHolder.kt             # Owns ExoPlayer instance, AudioAttributes, LoadControl
│   └── datasource/
│       └── RefreshingDataSource.kt    # Custom Media3 DataSource; catches 403 on loader thread
├── controller/
│   ├── PlaybackController.kt          # Orchestrates Play/Pause/Skip intents
│   ├── TransitionManager.kt           # Manages atomic direction-neutral transitionGenerationId
│   └── QueueManager.kt                # Owns in-memory queue, BackStack (50 max), shuffle state
├── continuity/
│   └── ContinuityEngineImpl.kt        # Pre-fetches recommendations at 30s threshold via CatalogRepository
├── tracker/
│   └── PlaybackClock.kt               # Computes millisecond scrub offsets without UI recomposition
└── client/
    ├── MediaControllerClient.kt       # UI bridge connecting Activity/ViewModels via MediaSession
    └── PlaybackStateMapper.kt         # Maps ExoPlayer states to domain PlaybackState
```

### Key Playback Boundaries:
- `SonaraPlaybackService` is the single Android `Service` entry point registered in `AndroidManifest.xml`.
- `RefreshingDataSource` is instantiated strictly inside the ExoPlayer `MediaSource.Factory` pipeline; it depends only on `StreamResolverPort` to request fresh stream URLs upon encountering HTTP 403/410.
- `MediaControllerClient` is provided to UI ViewModels as a clean Kotlin interface, ensuring no ViewModel directly references or manipulates `ExoPlayer` or `Service` internals.

## 9. Step 8: Lyrics Subsystem Architecture & Boundary

Lyrics processing involves pure parsing, temporal calculation, script transliteration, remote fetching, and UI presentation. The architectural boundaries are cleanly partitioned across **Domain**, **Data**, and **Feature**:

```text
1. Pure Domain Logic & Algorithms (Zero Android / UI Dependencies):
   domain/
   ├── model/
   │   └── Lyrics.kt                   # Immutable domain entities (PlainLyrics, SyncedLyrics, LyricLine)
   └── lyrics/
       ├── LrcParser.kt                # Pure Kotlin parser: string -> List<LyricLine>
       ├── LineSyncCalculator.kt       # Pure algorithm: (currentPositionMs, lines) -> activeLineIndex
       └── RomanizationEngine.kt       # Pure transliteration algorithm for non-Latin scripts (Devanagari, etc.)

2. Domain Repository Contract:
   domain/repository/LyricsRepository.kt

3. Data Remote & Cache:
   data/remote/providers/lrclib/       # LRCLIB API client and DTO mappers
   data/repository/LyricsRepositoryImpl.kt # Implements repository with in-memory positive cache

4. UI Feature Presentation:
   feature/lyrics/
   ├── LyricsSheet.kt                  # Full-screen / backdrop synchronized lyrics UI
   ├── LyricsViewModel.kt              # Injects LyricsRepository + PlaybackClock; uses LineSyncCalculator
   ├── LyricsUiState.kt                # UI state (Loading, Plain, Synced, Error)
   └── components/                     # Lyrics-specific UI components
       ├── LyricsLineItem.kt
       └── RomanizationToggle.kt
```

**Why pure algorithms belong in `domain/lyrics`**:
LRC parsing, line-matching mathematics, and script Romanization are pure Kotlin algorithms. Placing them in `domain/lyrics` ensures they can be tested at lightning speed with pure JUnit 4/5 (without Android SDK or Robolectric), can be shared across any future background workers or features, and do not leak UI dependencies.

## 12. Step 11: Architectural Anti-Patterns to Avoid

During implementation, the following structural and architectural anti-patterns are explicitly prohibited:

1. ❌ **The "Utils" Dumping Ground**: Do not create a generic `com.example.sonara.utils` package. Utilities must be co-located with their domain (e.g., `core.coroutines`, `core.ui`, or `domain.lyrics`).
2. ❌ **The "Managers" God-Package**: Do not create vague manager classes (`MusicManager`, `AppManager`, `DataManager`). Responsibilities must be specific (`PlaybackController`, `QueueManager`, `CatalogRepository`).
3. ❌ **`core.ui` Widget Pollution**: Do not dump feature-specific Composables into `core.ui`. `core.ui` is reserved exclusively for universal design tokens and base primitives.
4. ❌ **Redundant 1-Line UseCases**: Do not write UseCases that merely wrap a single repository call without adding business logic or coordinating multiple data sources.
5. ❌ **Direct ExoPlayer Leakage to UI**: ViewModels and Compose screens must NEVER hold a direct reference to `ExoPlayer`. All interactions must route through `MediaControllerClient`.
6. ❌ **Leaking Network DTOs into UI**: ViewModels and Composables must consume pure Domain models (`Track`, `Album`) or UI State models (`TrackUiModel`), never raw network response DTOs (`YouTubeVideoDto`).
7. ❌ **Domain Depending on Android / UI**: No class in `com.example.sonara.domain` may import `android.*`, `androidx.*`, `androidx.compose.*`, or `androidx.media3.*`.
8. ❌ **Circular Subsystem Dependencies**: `data` must never depend on `playback`, and `playback` must never depend on `data.repository` implementations (only on `domain.ports` and `domain.repository` contracts).

## 13. Step 12: Final Recommendation & Summary

### 13.1 Recommended Architecture Style
**Hybrid Layer-Feature Architecture (Strategy C)**:
- High-level system layers (`core`, `domain`, `data`, `playback`) own shared platform primitives, pure domain entities/algorithms, persistence/networking, and background media streaming.
- The UI layer (`feature`) is modularized cleanly by user-facing screen/flow (`home`, `search`, `library`, `player`, `queue`, `lyrics`, `settings`).

### 13.2 Key Boundaries Summary
- **UI Boundary**: ViewModels observe `MediaControllerClient` and `domain.repository` flows; emit immutable `UiState` to Jetpack Compose screens.
- **Lyrics Boundary**: Pure algorithms (`LrcParser`, `LineSyncCalculator`, `RomanizationEngine`) live in `domain.lyrics`; UI presentation lives in `feature.lyrics`.
- **Playback Boundary**: `SonaraPlaybackService` runs as an isolated Foreground Service hosting `ExoPlayer`; communicates with data layer strictly via `domain.ports.StreamResolverPort` and `domain.ports.ContinuityEnginePort`.
- **Data Boundary**: Repositories act as the single source of truth; Room provides local persistence; Proto DataStore manages proactive session snapshots; OkHttp/Retrofit communicates with external APIs.
- **Domain Boundary**: Pure Kotlin; zero framework dependencies; defines universal entities, pure algorithms, and IoC ports.

### 13.3 Implementation Readiness
This audit provides the definitive blueprint for file and package placement. When implementation is authorized, developers and agents will create files directly within these predefined packages without ambiguity or structural improvisation.
